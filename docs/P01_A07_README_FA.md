# P01-A07 — تفکیک نتیجهٔ HTTP از نتیجهٔ ثبت‌شدهٔ رویداد

## مرجع و مسئله

مرجع این بسته، سورس پس از کامیت `20accd25477af1c0ccb86deab15aa2f9b5fd798a` است. میان‌افزار قبلی برای POST/PUT/PATCH/DELETE با پاسخ کمتر از ۴۰۰، رویداد CREATE_OR_UPDATE یا DELETE موفق می‌ساخت؛ فرم نامعتبر با پاسخ ۲۰۰ یا انتقال ۳۰۲ بدون تغییر نیز ممکن بود عملیات موفق به نظر برسد.

## رفتار جدید

- میان‌افزار فقط یک رویداد SYSTEM با entity_type برابر http_request و نشان audit_scope برابر http_request ثبت می‌کند. business_outcome صریحاً UNKNOWN است.
- مقدار success در این نوع رویداد صرفاً معنای قدیمیِ «کد HTTP کمتر از ۴۰۰» را حفظ می‌کند؛ اثبات commit یا موفقیت عملیات نیست. کد ۴۰۰ یا ۵۰۰ هم به‌تنهایی اثبات بازگشت همهٔ تغییرات نیست.
- محتوا یا پیام پاسخ، فرم، POST، رمز و query string برای حدس نتیجهٔ عملیات خوانده یا ثبت نمی‌شوند. مسیر و نام view، مانند قبل، اطلاعات ردیابی درخواست هستند.
- ورود/خروج و GET همچنان از میان‌افزار عمومی خارج‌اند؛ رویدادهای امنیتی و عملیاتی صریح تولیدکنندگان موجود حفظ می‌شوند.
- «موفق/ناموفقِ ثبت‌شده» فقط نتیجه‌ای است که تولیدکنندهٔ رویداد صریح اعلام کرده است؛ نتیجهٔ تجاری از HTTP استنباط نمی‌شود. این بسته ادعا نمی‌کند تمام مسیرهای قدیمی، رویداد عملیاتی صریح و تراکنشی دارند. در نبود آن، نتیجهٔ واقعی عملیات نامشخص می‌ماند؛ ابزار برای همهٔ مسیرها نتیجه اختراع نمی‌کند.

## سوابق و گزارش

هیچ UPDATE یا DELETE روی سوابق تاریخی اجرا نمی‌شود. رکوردهای سازگار با امضای قدیمی میان‌افزار، فقط در زمان SELECT با برچسب «درخواست HTTP (قدیمی)؛ نتیجهٔ عملیات نامشخص» نمایش داده می‌شوند: method و action قدیمی متناظر، موجودیت و شناسهٔ خالی، مسیر آغازشده با /، شرح دقیق method + فاصله + path، و وجود هر دو کلید status_code و view_name لازم‌اند. صرف POST بودن، خالی‌بودن موجودیت یا داشتن status_code کافی نیست. این امضا سازگاری با ثبت HTTP قدیمی را نشان می‌دهد، نه موفقیت تجاری.

- کارت‌های نتیجهٔ موفق/ناموفق، درخواست‌های HTTP جدید و سوابق دارای امضای قدیمی را شامل نمی‌شوند. شمارش «تغییرات موفق ثبت‌شده» فقط رویدادهای صریح موفق با action تغییر را می‌شمارد؛ رویداد صریح ناموفق در آن نیست.
- تعداد کل سوابق حفظ می‌شود و شمار درخواست‌های HTTP و قدیمی جدا نمایش داده می‌شود. کاهش کارت نتیجهٔ موفق به معنی حذف داده نیست.
- فیلترهای yes/no به نتیجهٔ ثبت‌شدهٔ رویداد مربوط‌اند. http_ok/http_error به پاسخ HTTP جدید، و legacy_http به امضای قدیمی مربوط‌اند. صفحه و CSV از همان کوئری استفاده می‌کنند. فیلتر action بر مقدار اصلی ثبت‌شده در رکورد عمل می‌کند؛ action تاریخی بازنویسی نمی‌شود.
- تعداد و ترتیب ۱۲ ستون CSV، BOM فارسی، محافظ CSV گام A06، تاریخ شمسی، فیلتر شرکت، جست‌وجو و صفحه‌بندی حفظ می‌شوند؛ برچسب نوع و نتیجهٔ رویداد برای رفع ابهام تغییر کرده است.
- فهرست و فیلتر نتیجه در مدیریت Django نیز همان تفکیک را دارند؛ امکان ایجاد، ویرایش یا حذف ممیزی همچنان ممنوع است. ستون بولی خام success در فرم مدیریت جایگزین نمایش نتیجهٔ معنادار شده، نه اینکه از دیتابیس حذف شده باشد.

## محدودیت و نصب

این اصلاح schema، مدل، migration، نقش، عضویت، حساب و دادهٔ تجاری را تغییر نمی‌دهد. نصب‌کننده فقط سورس را با guard نسخه و هش و پشتیبان زمان‌دار تغییر می‌دهد؛ هنگام نصب به دیتابیس وصل نمی‌شود. کد آیندهٔ برنامه طبق رفتار ممیزی در زمان درخواست، رویداد جدید می‌نویسد.

آزمون‌ها با دادهٔ آزمایشی، فرم نامعتبر ۲۰۰، پاسخ ۳۰۲، خطاهای HTTP، عملیات rollback‌شده، عملیات صریح موفق بدون شمارش تکراری، تشخیص محدود سوابق، فیلتر، مجموع‌ها، CSV، مدیریت و صفحهٔ ممیزی را بررسی می‌کنند. آزمون محلی SQLite جایگزین نتیجهٔ واقعی PostgreSQL نیست.

طبق توافق کاهش تکرار تست، پس از check فقط فایل‌های auditlog/test_p01_a07_outcomes.py و auditlog/tests.py اجرا شوند. تست کامل در این مرحله درخواست نشده است. در شکست یا STOPPED ادامه ندهید. بررسی دستی فقط‌خواندنی باشد؛ برای آزمایش، عملیات روی حساب یا مشتری واقعی انجام ندهید.
