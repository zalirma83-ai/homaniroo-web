# E06 — یادداشت مستقل اپراتور برای همکاران

## مرجع و مجوز
- سورس مبنا: `a23b99e56e25986c04d8573afac6403c10c0663a`، پس از E05.
- گزارش schema-only کاربر: `homaniroo_E06_schema_20261027_215118_295102.json`؛ PostgreSQL 17.7، دیتابیس homaniroo_dev، search_path برابر public در کنار schema کاربر.
- طرح یک جدول مستقل، مرز شرکت و همکار و کنترل نسخه در همین گفتگو توسط کاربر تأیید شده است.
- نصب سورس، ساخت پشتیبان و اجرای migration سه اقدام جدا هستند. نصب‌کننده سورس هیچ migration یا اتصال دیتابیس ندارد.

## ساختار
مدل مدیریت‌شده PartnerNote در جدول جدید customers_partnernote ذخیره می‌شود؛ در تنظیم فعلی search_path، جدول در public ساخته خواهد شد.
فیلدها: id تولیدشده توسط دیتابیس، tenant_id، profile_id، body، version، updated_by_user_id، updated_by_name و updated_at.
قیدها: یکتایی tenant/profile، مثبت بودن شناسه محدوده و نسخه حداقل یک. شناسه ردیف جدید دستی تعیین نمی‌شود.
اتصال به EntityBusinessProfile در سرویس با همان tenant و نوع PARTNER و تأیید CONFIRMED کنترل می‌شود. به الگوی مدل‌های unmanaged موجود، شناسه‌های عددی ذخیره می‌شوند و FK فیزیکی جدید به جدول تاریخی تحمیل نمی‌شود؛ ایجاد PartnerNote به‌تنهایی هیچ داده core را تکمیل یا جابه‌جا نمی‌کند.

## رفتار
- در نبود یادداشت مستقل، textarea خالی است؛ یادداشت یا متن آمادهٔ وارداتی به آن کپی نمی‌شود.
- یادداشت قدیمی دسته‌بندی دیگر به‌عنوان یادداشت قابل ویرایش نمایش داده نمی‌شود؛ مقدار notes، sources و تمام داده‌های core بدون تغییر باقی می‌ماند.
- نوشتن، ویرایش و خالی‌کردن متن تا ۱۰۰۰۰ نویسه؛ متن ساده و autoescape، بدون تفسیر HTML.
- آخرین ویرایش‌کننده و زمان تهران نمایش داده می‌شود. جدول، نسخه فعلی متن را نگه می‌دارد؛ مرور کامل متن نسخه‌های قبلی قابلیت این بسته نیست.
- بدون تغییر واقعی، ردیف، نسخه، زمان یا ممیزی مصنوعی ساخته نمی‌شود. پاک‌کردن متن، ردیف و نسخه را نگه می‌دارد تا فرم قدیمی نتواند نوشته را دوباره برگرداند.
- شروع نوشتن و ویرایش در transaction و با قفل ردیف profile انجام می‌شود؛ ردیف core قفل می‌شود ولی هیچ فیلدش تغییر نمی‌کند. این کار نوشتن هم‌زمانِ اولین یادداشت را نیز پوشش می‌دهد.
- نسخه ارسالی قدیمی: پاسخ 409، حفظ متن تایپ‌شده در فرم، بدون بازنویسی متن جدید. کاربر باید متن خود را کپی و صفحه را دوباره باز کند؛ ادغام یا retry خودکار وجود ندارد.
- POST با CSRF، مسیر ثابت بازگشت به همان همکار؛ پارامتر next پذیرفته نمی‌شود. مقدار نامعتبر 400، نقش نامجاز 403 و profile غیرمجاز 404.
- عملیات موفق ممیزی می‌شود، بدون ثبت متن یادداشت در لاگ/metadata. اگر ممیزی عملیات ثبت نشود، تغییر یادداشت هم rollback می‌شود.

## مجوز و مرز شرکت
سوپرادمین Django فعال مجاز است. برای سایر کاربران، هویت تجاری متصل، عضویت فعال در شرکت فعال و نقش همان شرکت از COMPANY_ADMIN/SENIOR_OPERATOR/OPERATOR لازم است. صرف گروه OPERATOR یا نقش شرکت دیگر مجوز ویرایش نیست. این محدودیت فقط مسیر جدید E06 را پوشش می‌دهد و بازنویسی سراسری RBAC پروژه نیست.
کاربر فقط‌خواندنیِ مجازِ صفحه، متن همان همکار در همان شرکت را می‌بیند اما فرم و مسیر نوشتن برایش مجاز نیست.

## مرز تغییر
قالب partner_detail، مدل و migration جدید، سرویس و فرم، مسیر و view و تست‌ها؛ بدون تغییر تم/فونت، طبقه‌بندی، وضعیت مشتری، مالکیت، CSV، قراردادها، انرژی و انتشار.
متن مشخص‌شده برای E07 عمداً باقی است؛ آن اصلاح در گام خودش انجام می‌شود.
Migration جدید فقط 0007_partnernote و شامل CreateModel است؛ داده‌ای منتقل، کپی یا backfill نمی‌شود. migrations قدیمی تغییر نکرده‌اند.

## نصب مرحله‌ای
۱. توقف runserver و ابزارهای نویسنده فایل؛ کنترل و نصب سورس محافظت‌شده در ریشه پروژه با .venv فعال؛ helper بیرون پروژه در Downloads بماند.
۲. check، بررسی هماهنگی migration با مدل و برنامهٔ فقط‌خواندنی migration. تا آماده‌شدن جدول، سرور را راه‌اندازی نکنید.
۳. پشتیبان تازهٔ PostgreSQL بیرون پروژه و کنترل فهرست آرشیو و checksum؛ صرف وجود پشتیبان، تأیید آزمون بازیابی واقعی نیست.
۴. فقط پس از تأیید بررسی‌ها، اجرای migration مشخص به‌صورت جدا؛ --fake، rollback یا اجرای دوبارهٔ انتقال دسته‌بندی ممنوع است.
۵. کنترل اعمال migration، تست هدفمند و کامل روی PostgreSQL کاربر و پذیرش دستی هر دو شرکت و نقش‌ها.
۶. بررسی status و diff --check و ثبت فقط مسیرهای بسته؛ secret، پشتیبان، helper دانلودی، templates.zip یا فایل‌های نامرتبط stage نشوند. هش واقعی از خروجی کاربر ثبت شود.
در STOPPED، traceback، تست ناموفق یا نتیجه مبهم، ادامه متوقف می‌شود.

## شواهد محیط دستیار
تست‌های ذخیره‌سازی در SQLite ایزوله با سازگارکنندهٔ موقت نام جدول‌های core اجرا شده‌اند؛ فایل‌های تنظیم و سازگارکننده داخل بسته پروژه قرار نمی‌گیرند. migrationهای تاریخی PostgreSQL در این محیط اجرا نشده‌اند. یک تست قفل هم‌زمان مخصوص PostgreSQL روی SQLite عمداً skipped است. نتیجه محلی هرگز جای نتیجه واقعی PostgreSQL کاربر اعلام نمی‌شود.
تا دریافت خروجی کاربر، نصب واقعی، ساخت جدول در homaniroo_dev، تست PostgreSQL، پذیرش دستی و کامیت E06 تأیید نشده‌اند.
